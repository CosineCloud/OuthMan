# Integrating an app with OuthMan API v1

This guide describes the API implemented in `server.py`. Use it for every Cosine app that needs OuthMan verification. Examples use an imaginary application called XYZ. Replace placeholder values; no real credentials belong in this document.

## 1. What the mechanism does

OuthMan verifies a user's existing OuthMan credentials and a manually generated six-digit code. XYZ's backend also authenticates itself and supplies a secret issued specifically for that app/user pair. After verification, XYZ confirms a short-lived authentication PIN before creating its own session.

There are two separate flows:

- **Registration/linking:** call `/enroll` once to link an existing OuthMan account to a local XYZ account.
- **Login:** call `/verify`, then `/confirm`, every time XYZ requires OuthMan authentication.

The user enters only their username/email, password, and six-digit code. XYZ automatically handles app credentials, the user key, request ID, and authentication PIN on its backend.

This is OuthMan's custom REST protocol. It does not implement OAuth, OpenID Connect, JWT, or authenticator-app TOTP. An OuthMan six-digit code is randomly generated on demand, rather than derived from a shared TOTP seed.

```mermaid
sequenceDiagram
    participant U as User
    participant X as XYZ backend
    participant O as OuthMan
    U->>O: Generate a code (60-second lifetime)
    U->>X: Username, password, six-digit code
    alt First-time linking
        X->>O: POST /enroll + app credentials
        O->>O: Check credentials and consume code
        O-->>X: user_id + once-visible user_key
        X->>X: Save linked identity and encrypted key
    else Subsequent login
        X->>X: Validate local password; create pending request_id
        X->>O: POST /verify + credentials, code, user_key, request_id
        O->>O: Check everything and consume code
        O-->>X: auth_pin (30-second lifetime)
        X->>O: POST /confirm + username, auth_pin, request_id
        O->>O: Validate and consume PIN
        O-->>X: verified + app_id + user_id + request_id
        X->>X: Match pending login and create XYZ session
        X-->>U: Login successful
    end
```

## 2. Values and where they belong

| Value | Meaning | Where to keep it |
| --- | --- | --- |
| `app_id` | Identifies XYZ; generated by the admin portal, not the app name | XYZ backend configuration |
| `app_secret` | 128-bit app credential, shown once when an app is created | Backend secret manager/environment |
| `username` | Existing OuthMan username; may be an email address | XYZ account record |
| `password` | Existing OuthMan password supplied by the user | Request memory only; save only a password hash for local login |
| `code` | Six ASCII digits, including any leading zero | Request memory only |
| `user_id` | Immutable OuthMan account ID returned by enrollment | XYZ account record, together with provider identity |
| `user_key` | 128-bit secret issued to one app/user pair | Encrypted in XYZ storage against its local user ID |
| `request_id` | Random value identifying a single pending XYZ login | XYZ server-side pending login session |
| `auth_pin` | Random 128-bit proof returned by verification | XYZ backend memory until confirmation |

Generated app secrets, user keys, and authentication PINs contain **32 hexadecimal characters**. App IDs contain 16 hexadecimal characters. OuthMan stores hashes of the secrets and PINs. XYZ must retain its actual user key securely because it must send the key on future logins.

The authentication PIN is separate from the user's six-digit code. It is not another value for the user to enter, and it is not a signed token that XYZ can validate offline.

## 3. Setup for each app

1. Start OuthMan and sign in as an administrator. Complete the required default credential change.
2. In **Connect your apps**, enter an application name and create an app credential.
3. Save the returned app ID and complete app secret immediately. The secret is shown once. Use a different app credential for each application and environment.
4. Configure the XYZ backend with `OUTHMAN_BASE_URL`, `OUTHMAN_APP_ID`, and `OUTHMAN_APP_SECRET`.
5. Add local account fields for the OuthMan provider/base URL, `user_id`, canonical username, and encrypted `user_key`. Enforce uniqueness of the provider/user ID binding.
6. Add a server-side pending login record containing the local account ID, expected OuthMan user ID, random request ID, expiration, and a reference to the initiating browser session.

Local base URL: `http://127.0.0.1:10070`. Use HTTPS for network deployment. On a different server or in a container, `127.0.0.1` points to that server/container, not the Mac running OuthMan; configure a reachable OuthMan address.

Users must already have registered in OuthMan with an admin invitation. `/enroll` links an account; it does not create an OuthMan account. Email-shaped usernames are accepted, but the current implementation does not verify ownership of the email address.

## 4. Common REST contract

All integration requests use `POST` and these headers:

```text
Content-Type: application/json
X-OuthMan-App: YOUR_APP_ID
Authorization: Bearer YOUR_APP_SECRET
```

No OuthMan browser cookie is required. Calls must originate from XYZ's backend. Do not call these APIs directly from browser JavaScript: that would expose backend secrets. The current server rejects cross-origin browser requests and does not provide a browser CORS integration.

Use a JSON serializer for real input, not string concatenation. Send codes as strings (`"012345"`), not numbers. Send request bodies under 8 KB. `expires_at` is a Unix timestamp in seconds, potentially with a fractional part.

The curl commands below are manual development examples. Replace uppercase placeholders; do not include terminal prompts or Markdown links in commands.

## 5. Registration: POST /api/v1/enroll

XYZ collects the user's matching OuthMan username and password, plus a fresh code generated in OuthMan. The app secret identifies XYZ without a browser session.

```sh
curl --fail-with-body 'http://127.0.0.1:10070/api/v1/enroll' \
  -H 'Content-Type: application/json' \
  -H 'X-OuthMan-App: YOUR_APP_ID' \
  -H 'Authorization: Bearer YOUR_APP_SECRET' \
  --data '{"username":"person@example.com","password":"USER_PASSWORD","code":"012345"}'
```

Successful response: **201 Created**.

```json
{
  "app_id": "YOUR_APP_ID",
  "user_id": 42,
  "username": "person@example.com",
  "user_key": "ONCE_VISIBLE_128_BIT_USER_KEY"
}
```

XYZ must check the app ID and response shape, then atomically save the OuthMan identity and encrypted key with the local account. Never return the enrollment response to the browser. The key is tied to the app and OuthMan user ID; do not store it against the plaintext password.

Enrollment consumes the six-digit code. The user needs a **new code** for a subsequent login. An existing binding returns 409 and cannot retrieve or replace the old key. Persist the enrollment response durably: if it is lost after OuthMan commits, repeating enrollment cannot recover the key. There is currently no self-service user-key recovery endpoint.

Enrollment does not return an authentication PIN. An app may complete its registration after successful linking; if its policy requires a separate login, run the full login flow with a fresh code.

## 6. Login: POST /api/v1/verify

XYZ should first verify its local password hash. Load the encrypted user key from the local account, decrypt it on the backend, and generate a new cryptographically random request ID. A UUID v4 or `secrets.token_urlsafe(32)` is suitable. The API accepts request IDs of 16–128 characters, but XYZ is responsible for randomness and uniqueness.

Bind this ID to the initiating pending login session. Never use a fixed example ID in production, and never trust a browser-provided user key or expected user ID.

```sh
curl --fail-with-body 'http://127.0.0.1:10070/api/v1/verify' \
  -H 'Content-Type: application/json' \
  -H 'X-OuthMan-App: YOUR_APP_ID' \
  -H 'Authorization: Bearer YOUR_APP_SECRET' \
  --data '{"username":"person@example.com","password":"USER_PASSWORD","code":"654321","user_key":"STORED_USER_KEY","request_id":"UNIQUE_RANDOM_LOGIN_REQUEST_ID"}'
```

Successful response: **200 OK**.

```json
{
  "auth_pin": "SHORT_LIVED_128_BIT_AUTHENTICATION_PIN",
  "expires_at": 1900000030.0,
  "request_id": "UNIQUE_RANDOM_LOGIN_REQUEST_ID"
}
```

OuthMan checks the app credential, OuthMan username/password, unexpired six-digit code, and app/user key. Success consumes the code atomically: simultaneous verification requests cannot both use it.

**Do not create a XYZ login session yet.** Check that the returned request ID matches the pending login, and immediately confirm the returned PIN on the backend.

## 7. Final check: POST /api/v1/confirm

```sh
curl --fail-with-body 'http://127.0.0.1:10070/api/v1/confirm' \
  -H 'Content-Type: application/json' \
  -H 'X-OuthMan-App: YOUR_APP_ID' \
  -H 'Authorization: Bearer YOUR_APP_SECRET' \
  --data '{"username":"person@example.com","auth_pin":"PIN_FROM_VERIFY","request_id":"UNIQUE_RANDOM_LOGIN_REQUEST_ID"}'
```

Successful response: **200 OK**.

```json
{
  "verified": true,
  "app_id": "YOUR_APP_ID",
  "user_id": 42,
  "username": "person@example.com",
  "request_id": "UNIQUE_RANDOM_LOGIN_REQUEST_ID"
}
```

OuthMan checks that the PIN is unexpired and belongs to the same app, user, and request ID. Confirmation consumes the PIN, so it cannot be replayed. Its lifetime is 30 seconds from verification.

Before granting login, XYZ must check all of the following:

- HTTP status is 200 and `verified` is the boolean `true`.
- `app_id` equals the configured app ID.
- `user_id` equals the immutable ID saved during enrollment.
- `request_id` equals the pending login request ID.
- The pending login belongs to this local account and initiating browser session, is unexpired, and has not been completed.

Then atomically mark the pending login complete and create/rotate the XYZ session. Return only the app's normal login result/session cookie to the browser. The XYZ app owns its session lifetime and logout behavior; OuthMan does not create or revoke XYZ sessions automatically.

## 8. Backend implementation outline

This is framework-independent pseudocode. `store`, `decrypt`, password validation, and session creation represent the integrating app's own implementations.

```text
register(input, browser_session):
    validate local registration input
    reserve local registration/account identity
    linked = POST /enroll(input.username, input.password, input.code)
    require status 201 and linked.app_id == configured_app_id
    validate linked.user_id, linked.username, and linked.user_key
    securely persist local account + password hash + provider/user_id
        + canonical username + encrypted linked.user_key
    discard plaintext password, code and response secret from request memory
    return registration success without OuthMan secrets

login(input, browser_session):
    account = find local account(input.username)
    require valid local password hash and an enrolled OuthMan identity
    pending = store.create_pending_login(
        account.id, account.outhman_user_id, browser_session,
        cryptographically_random_request_id(), short_expiration)
    verified = POST /verify(
        account.outhman_username, input.password, input.code,
        decrypt(account.encrypted_user_key), pending.request_id)
    require status 200 and verified.request_id == pending.request_id
    confirmed = POST /confirm(
        account.outhman_username, verified.auth_pin, pending.request_id)
    require status 200 and confirmed.verified is true
    require confirmed.app_id == configured_app_id
    require confirmed.user_id == account.outhman_user_id
    require confirmed.request_id == pending.request_id
    atomically consume pending login for this account/browser session
        and create/rotate the XYZ session
    return normal XYZ session response, never the OuthMan PIN
```

Apply bounded HTTP timeouts, verify TLS certificates, and do not follow unexpected redirects carrying credentials. Handle failures without logging request bodies or secret-bearing responses. Never fall back to password-only login when OuthMan is unavailable.

## 9. Expiry, replay, and failures

| Item | Current behavior |
| --- | --- |
| Six-digit code | Expires 60 seconds after generation; no automatic refresh |
| Regenerated code | Replaces the previous code immediately |
| Successful enrollment or verification | Consumes the code across all apps |
| Failed credential/code/key validation | Does not consume an otherwise valid code; failures are throttled |
| Authentication PIN | Expires after 30 seconds; consumed by successful confirmation |
| App credential | Valid until admin revocation; no automatic expiry |
| Per-user key | Valid for its app/user pair until the app is revoked; no rotation endpoint |
| App revocation | Blocks further integration calls and deletes pending PINs; does not end existing XYZ sessions |

| HTTP status | Meaning / action |
| --- | --- |
| 200 | Verification/confirmation succeeded; validate response fields |
| 201 | Enrollment succeeded; securely persist returned key |
| 400 | Invalid JSON, fields, request ID, or body format |
| 401 `Invalid app credentials.` | Wrong/missing app ID, Bearer secret, or revoked app |
| 401 `Verification failed or expired.` | Wrong user credentials/key/code/PIN, expired or consumed value, or incorrect binding |
| 403 | For example, a cross-origin browser request; use backend calls |
| 404 | Unknown API endpoint |
| 409 | Account already linked; use the originally saved user key |
| 429 | Too many failures; stop automatic retries and wait for the throttle window |
| Timeout/network error/5xx | Do not grant login; offer a fresh attempt |

Ten failed integration requests trigger throttling for the caller IP and/or username within a 15-minute window. Account throttling spans apps. Many users behind one XYZ backend share a caller IP, so an IP throttle can affect other users too. There is currently no `Retry-After` header. Audit IP/browser values identify the calling backend, not the user's device.

Requests are not idempotent. A network timeout can occur after consumption:

- After `/verify` or `/confirm`, restart login with a fresh code and new request ID if the outcome is uncertain. Never assume authentication succeeded.
- After `/enroll`, the account may already be linked even if XYZ lost the response. There is no key retrieval API; use controlled administrator recovery. A fresh code alone cannot recover the lost user key.

## 10. Common curl problems

- **`dquote>` or `quote>` prompt:** an unmatched quote remains open. Press Ctrl+C and paste the whole corrected command.
- **`&#x20;`:** HTML for a space; do not paste it into Terminal.
- **Malformed URL:** use a plain `http://…` or `https://…` URL, not `[URL](URL)` or `http\://…`.
- **Broken multiline command:** each continuation `\` must be the last character on its line, with no trailing spaces. Do not copy shell prompts.
- **Invalid app credentials:** use the generated app ID, not the app name. Include the literal `Bearer ` prefix and the full app secret. Keep the closing quote after every header.
- **Invalid user verification:** check the matching OuthMan password, app-specific user key, and a newly generated six-digit code. Preserve leading zeroes.
- **Confirmation fails:** use the PIN from the immediately preceding verification, the same username/app/request ID, and confirm within 30 seconds. Do not substitute the six-digit code for the PIN.
- **New UI but access denied:** restart `python3 server.py` after backend updates and refresh the browser.

For automated apps, use the language's HTTP client and JSON encoder. Manual shell quoting is not an integration strategy; credentials containing quotes or other special characters must be serialized correctly.

## 11. Deployment and acceptance checks

Keep backend secrets out of frontend bundles, browser storage, URLs, analytics, and logs. Encrypt saved user keys with a key managed separately from the account database. Back up the encrypted records and their encryption key securely. Protect XYZ's own login endpoints with CSRF protection, rate limiting, and secure session cookies.

The current OuthMan implementation has no per-user key recovery/rotation API, password reset/synchronization API, or automatic app-secret rotation. Plan administrator recovery before rollout. If XYZ stores a local password hash, define how password changes stay synchronized with OuthMan. Shared credentials mean XYZ receives the OuthMan password during authentication; restrict integration to trusted apps.

Before exposing the current local server publicly, configure HTTPS, production serving, and secure OuthMan cookies as described in README.md. This protocol guide is not a claim that the local development server is ready for unrestricted production deployment.

Test each app integration before release:

- Enroll an existing OuthMan user, save the key, then log in with a fresh code.
- Reject wrong passwords, wrong keys, revoked app credentials, and expired codes/PINs.
- Preserve codes starting with zero.
- Reject a code used a second time, including simultaneous requests.
- Reject a PIN used twice, from a different app/user, or with a different request ID.
- Check the confirmed immutable user ID before creating the local session.
- Deny login on timeout, malformed response, and OuthMan outage.
- Verify that secrets are absent from browser responses and application logs.
- Exercise enrollment-response loss and documented administrator recovery.

The OuthMan repository's own API tests run with `python3 -m unittest -v`. Each integrating app also needs tests for its local account persistence, pending-session binding, response checks, and final session creation.

## Group authorization and account suspension

An administrator must assign each user and app to a shared access group before enrollment, verification, or confirmation. Missing group authorization returns 403. Group changes invalidate pending PINs; begin again with a fresh code. Existing app bindings do not bypass group authorization.

Accounts blocked by their code-generation limit return 423 during the five-minute block and subsequent suspension. Only an administrator can release the account and reset its count. Treat both responses as authentication failures. These restrictions do not revoke sessions already issued by an integrating app.

## Integration IP ACL

Before calling `/api/v1/enroll`, `/api/v1/verify`, or `/api/v1/confirm`, an admin must configure **API IP allowlist (ACL)** in the dashboard. Enter backend IPv4/IPv6 addresses or CIDR networks, one per line. The default empty list denies all integration requests (403), including localhost. Add `127.0.0.1` for local curl calls. This applies to every API client, regardless of User-Agent. App credentials and group authorization are still required. Browser administration is unaffected.

The ACL uses the directly connected peer IP and ignores forwarded headers. Behind a reverse proxy it sees the proxy IP; configure original-client restrictions at that proxy. Saving the ACL invalidates pending PINs; restart authentication with a fresh code.


Backup operations are documented separately in [backup_feature.md](backup_feature.md).

## Manual approval and browser binding

Invitation-based registration now returns `202 {"pending_approval":true}` without a session. An administrator must approve the account under Settings → Users & access. The approved user signs in to OuthMan, binding their browser before generating codes or enrolling/verifying through an app. Approval does not automatically grant group access. Pending and unbound non-admin accounts fail integration verification. Releasing a browser binding invalidates OuthMan sessions, current codes, and pending PINs; the user must sign in again to bind a browser and generate a new code.

OuthMan browser requests send an `X-OuthMan-Device` fingerprint header and an HttpOnly device cookie, both checked against the bound account. Integrating backends do not supply or copy this cookie/header: they continue using the documented app protocol and user-generated codes. Browser binding controls the OuthMan browser session, while each integrating app owns its own browser/device policies and existing sessions. Never grant access on any integration failure.

Accounts blocked by three failed browser logins cannot use integration authentication until an administrator releases their login block. OuthMan clears active codes and pending PINs when the block is triggered; start again with a fresh code after release. The counter covers browser `/api/login` failures; integration endpoints retain their existing failure throttles.

Administrative suspension prevents integration authentication until Resume. Deletion removes the user’s app links and active codes/PINs; fail closed on subsequent authentication failures. User IDs are never reused for a replacement account. Existing sessions issued by an integrating app still require that app's own revocation policy.

For app-scoped or centralized log collection, see [LOG_API_INT.MD](LOG_API_INT.MD). Log export uses dedicated read-only keys, separate from app credentials.
